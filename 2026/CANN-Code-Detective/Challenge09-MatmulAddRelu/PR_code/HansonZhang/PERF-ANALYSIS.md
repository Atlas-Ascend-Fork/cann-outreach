## 2. 算术强度与 roofline 判据

```
AI = FLOPs / GM 字节
   = 33,554,432 / 786,432
   = 42.67 FLOP/B
```

**判据**：

```
t_compute = 33,554,432 / P
t_memory  =    786,432 / BW

t_compute ≤ t_memory  ⟺  P / BW ≥ 42.67 FLOP/B
```

即：**只要芯片的「Cube 浮点吞吐 : HBM 带宽」比值超过约 43，本算子就是
compute-bound（计算受限）**。昇腾系列 Cube 与 HBM 的算力带宽比通常在数百量级，
因此本实现是**明确计算受限**的——优化重点不在减少访存，而在**喂满 Cube**。

> 这一结论是解析式的，不依赖具体型号；换任何一代昇腾芯片都成立。

## 3. 片上流量：真正制约 Cube 利用率的部分

GM 流量只走一次，但**片上**流量决定了 Cube 能不能连续工作：

| 环节 | 字节数 | 说明 |
|:--|--:|:--|
| GM → L1 | 262,144 | A、B 各整体入 L1（TODO1） |
| L1 → L0A/L0B | 262,144 | 4 个分片累计 = 整份 A、B |
| **L0C 累加读写** | **1,048,576** | 4 次 `mmad`，每次读改写整块 256 KiB |
| L0C → UB | 262,144 | `SPLIT_M` 分发 |

**L0C 累加的 1 MiB 片上读写是最大的单项开销** —— 它是 GM 流量的 4 倍。
这是 `init_c` 分支的直接后果：第 0 片覆盖写入，后 3 片必须
「读 L0C → Cube 相加 → 写回 L0C」。

> 结论：若要进一步提速，减少 K 分片数（即增大 `L0_K`）能同比降低 L0C 流量。
> 当前 `L0_K=64` 是任务书给定的模板参数，不在补全范围内，故维持原值。

## 4. 同步结构：Cube 与 Vector 严格串行

- Cube → Vector 仅有一条跨核通道 `cross_flag fix_done`
- Cube 段内 4 轮 K 分片串行，每轮 `mutex_l0` lock/unlock 一对
- 全核 `mutex_l0c`、`mutex_acc`、`mutex_x` 合计约 10 对 lock/unlock

由于 `block_num=1`，且 Vector 工作必须等 `fix_done` 置位后开始，
**Cube 段与 Vector 段完全串行，不存在任何重叠**。

**这带来一个可量化的判断**：题目固定 256³ 规模，`block_num=1`，
单个 AICORE 要独自完成 33.55 MFLOP 的 Cube 工作加 13.1 万次向量操作。
矩阵规模偏小，**核数与并行度无法通过调优放大**——这是题目设定决定的，
不是实现缺陷。真正可优化的空间有限。

## 5. Vector 侧指令量

每 AIV：

```
元素数   = 128 × 256 = 32,768
每元素算子 = add + max = 2
SIMD 指令 = 32,768 / 64 = 512 条（每条含 add + max 两步）
```

每行恰好 4 个完整 64-lane 向量，**无需尾掩码**，无边界浪费。
`SPLIT_M` 把 256 行均分为 128/128，**整除无余数，两个 AIV 负载完全均衡**，
不存在因分片不均导致的 tail effect。

这两点是本实现设计上正确的地方，也是任务书选择 `SPLIT_M` 的原因。
